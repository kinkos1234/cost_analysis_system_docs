# 01. CAS_Decision_n_Data_Immutability_Contract

## 1. Document Purpose

CAS에서 다루는 데이터와 판단 결과에 대해 **누가 결정하는가(Decision Ownership)**와 **한 번 생성된 데이터를 바꿀 수 있는가(Data Immutability)**를 정한다.

이후의 데이터 모델, 계산 로직, API, UI, 운영 정책은 모두 이 문서의 원칙 안에서 설계되어야 한다.

---

## 2. Core Principles

### 2.1 Decision Ownership Principle

CAS에서 발생하는 모든 결과는 아래 세 범주 중 하나에 속해야 하며, 범주 간 책임은 혼합될 수 없다.

| Category       | Description                      | Owner                   |
| -------------- | -------------------------------- | ----------------------- |
| Fact           | 사용자가 입력하거나 외부 시스템으로부터 수집된 원본 데이터 | Human / External System |
| Derived Value  | 규칙 기반 연산을 통해 산출된 수치 결과           | Rule Engine             |
| Interpretation | 결과에 대한 설명, 해석, 코멘트               | Human                   |

※ LLM은 CAS v1에서 **어떠한 Category의 Owner도 아니다**.
※ Phase 2에서 ML 기반 목표 범위 제안이 도입되더라도, ML 출력은 **Interpretation** 범주에 해당하며 Decision Ownership을 갖지 않는다 (00 §9.3 참조).

---

### 2.2 Temporal Immutability Principle

CAS는 특정 시점의 판단이 이후 환경 변화로 인해 왜곡되는 것을 허용하지 않는다.

그래서 CAS는 주요 데이터를 모두 **Snapshot 단위로 고정**한다.

* Snapshot은 생성 이후 **수정·삭제·재계산이 불가**하다.
* Snapshot은 새로운 Snapshot으로만 대체될 수 있다.
* 모든 분석 결과는 반드시 특정 Snapshot을 참조해야 한다.

Snapshot 불변성은 두 겹으로 걸어 놓았다.

* **데이터베이스 수준:** PostgreSQL의 UPDATE/DELETE 차단 Trigger (10 §3.1 참조)
* **애플리케이션 수준:** Validation Engine의 불변성 검증 (10 §4.1 참조)

---

## 3. Stage-based Snapshot Policy

### 3.1 Stage Definition

Stage란, 수주 이후 개발·양산 과정에서 비용이 결정되는 시점을 말한다.

기본 Stage 체계는 다음과 같다.

1. Bid (수주) — `BID`
2. Design Cost Review – 1st (설계원가 1차) — `DC1`
3. Design Cost Review – 2nd (설계원가 2차) — `DC2`
4. Design Cost Review – 3rd (설계원가 3차) — `DC3`
5. SOP Initial Price (양산 초도가) — `SOP`
6. Post-SOP Design Change – Nth (양산 후 설변) — `POST_SOP_N` (N=1,2,3,...)

※ Post-SOP Stage는 개수 및 시점이 사전에 고정되지 않는다.

> **v1.3 변경:** Post-SOP Stage 코드에 순번(N)을 부여하여 복수 Post-SOP Snapshot 간 순서를 식별할 수 있게 한다. 상세는 03 §3.2 참조.

---

### 3.2 Snapshot Creation Rule

* 각 Stage 진입 시점에 **Stage Snapshot**이 생성된다.
* Stage Snapshot은 해당 Stage에서의 모든 차종·품번 비용 구조를 포함한다.
* Snapshot 생성 이후:

  * 기존 Snapshot은 변경 불가
  * 다음 Stage Snapshot은 반드시 직전 Snapshot을 참조하여 생성된다.

Stage 전환 합법성은 Validation Engine에 의해 검증된다: `base_snapshot_id`는 직전 `stage_order`를 가진 Stage의 Snapshot을 참조해야 한다 (10 §4.2 참조).

## 4. Data Mutability Matrix

| Data Type         | Example             | Mutability                   | Owner           | Enforcement             |
| ----------------- | ------------------- | ---------------------------- | --------------- | ----------------------- |
| Raw Input Data    | 품번 단가, Usage, Stage | Editable (Pre-Snapshot)      | Analyst         | —                       |
| Snapshot Data     | Stage별 비용 구조        | Immutable                    | System          | DB Trigger + Validation |
| Reference Data    | 인건비, 환율             | Editable (Approval Required) | Analyst → Manager | 승인 워크플로               |
| Derived Metrics   | 제조원가율, 총비용율         | Immutable                    | Rule Engine     | 계산 엔진 산출 전용            |
| Target Evaluation | 목표 달성 여부            | Immutable                    | Rule Engine     | 계산 엔진 산출 전용            |
| Comment           | 마진 변동 사유            | Editable                     | Human           | —                       |

> **v1.3 변경:** v1.2의 `Staff` → `Analyst`로 수정. 온톨로지 기반 Enforcement를 DB 제약 + Validation Engine으로 대체.

---

## 5. Recalculation & Versioning Policy

* 모든 계산 로직은 버전 관리된다.
* 각 Snapshot에는 다음 메타데이터가 기록된다.

  * 적용된 계산 로직 버전 (`calculation_version`)
  * 적용된 기준 데이터 버전 (`reference_data_version`)
* 기준 데이터 변경은 **과거 Snapshot에 영향을 미치지 않는다**.
* 새로운 기준 데이터는 이후 생성되는 Snapshot에만 적용된다.

---

## 6. Human Intervention Boundary

* 사용자가 직접 할 수 있는 건 **Fact 입력과 Interpretation 작성**뿐이다.
* 사용자는 어떠한 경우에도 Derived Value 및 Evaluation Result를 직접 수정할 수 없다.
* 승인(Manager)은 데이터 변경이 아니라 **변경 요청의 승인 행위**로만 기록된다.

---

## 7. AI Usage Policy (Explicit Non-Usage)

* CAS v1은 LLM API를 사용하지 않는다.
* 자동 판단, 목표 설정, 평가 결과 생성에 AI를 사용하지 않는다.

※ Phase 2에서 ML 기반 목표 범위 제안이 도입될 경우, 본 문서의 Decision Ownership 원칙을 침해하지 않는 범위에서만 허용된다 (00 §9 참조).

---

## 8. 준수 범위

이 원칙에 맞지 않는 구현은 수정 대상이다. DB 제약 위반이나 Validation Engine 검증 실패도 마찬가지로 다룬다. 시스템 운영 기간 중 이 문서의 원칙 자체를 바꿀 일은 없다.
