# 03. CAS_Data_Model_n_Snapshot_Schema

## 1. Document Purpose

01·02문서의 원칙이 DB 레벨에서도 지켜지도록, CAS의 주요 엔티티·관계·Snapshot 구조를 정의한다.

DB 설계 시 성능이나 편의를 위해 여기 정한 규칙을 깨면 안 된다.

---

## 2. Core Modeling Principles

### 2.1 Snapshot as First-class Entity

* Snapshot은 단순한 상태 값이 아니라 **독립된 1급 엔티티**이다.
* 어떠한 비용 데이터도 Snapshot에 귀속되지 않으면 유효하지 않다.

### 2.2 Stage ≠ Snapshot

* Stage는 **의사결정 이벤트의 유형(Type)** 이다.
* Snapshot은 **특정 Stage에서 생성된 시간 고정 인스턴스**이다.

### 2.3 Bid Snapshot Uniqueness

* 각 Vehicle은 **정확히 하나의 Bid Snapshot**을 가진다.
* Bid Snapshot은 모든 비교·평가의 기준(anchor)이다.

### 2.4 Single Store Principle

* CAS의 모든 데이터는 **PostgreSQL 단일 스토어**에 영속화된다.
* 도메인 무결성은 DB 제약(FK, CHECK, UNIQUE, Trigger)과 Validation Engine의 이중 검증으로 보장된다 (10. Constraint Spec 참조).

> **v1.3 변경:** v1.2의 Dual Representation Principle(PostgreSQL + Triple Store) 제거. 단일 스토어로 단순화.

## 3. Core Entities

### 3.1 Vehicle

**Purpose:** 분석의 최상위 단위

Key Fields:

* vehicle_id (PK)
* customer_group — 고객사 그룹 (HMC 등)
* vehicle_code — 차종 코드
* vehicle_name — 차종명
* model_name — 모델명
* customer_name — 고객사명
* purchaser_dept / purchaser_name / purchaser_title — 구매측 담당자 정보
* bid_year — 입찰 년도 (Integer, YYYY)
* sop_year / sop_month — 양산 개시 시점 (Integer, YYYY / MM)
* customer_region — 고객 생산지
* production_region — 내부 생산지 (인건비 산출 기준)
* has_buyback — 바이백 여부 (Boolean)
* currency — 통화 기준 (KRW, INR 등)
* multi_cr_rate — 연차별 판매가 인하율 (%, 기본 3%)
* dispatch_labor_rate — 파견인건비 비율 (%)
* office_expense ~ sample_expense — 개발비 항목 (7개 필드)
* tooling_cost / process_investment — C-Type 투자비
* is_active — 활성 여부
* memo — 메모
* created_at / updated_at

---

### 3.2 Stage

**Purpose:** 비용 결정 단계의 유형 정의

Key Fields:

* stage_code (PK) — `BID`, `DC1`, `DC2`, `DC3`, `SOP`, `POST_SOP_N`
* stage_name
* stage_order (Integer)
* is_post_sop (Boolean)

**Stage Order 규칙:**

| stage_code | stage_order | 비고 |
|---|---|---|
| BID | 1 | 고정 |
| DC1 | 2 | 고정 |
| DC2 | 3 | 고정 |
| DC3 | 4 | 고정 |
| SOP | 5 | 고정 |
| POST_SOP_1 | 6 | 동적 생성, N=1 |
| POST_SOP_2 | 7 | 동적 생성, N=2 |
| POST_SOP_N | 5+N | 동적 생성 |

> **v1.3 변경:** Post-SOP Stage에 순번(N)을 부여하여 `stage_order = 5 + N`으로 산정. v1.2에서 모든 Post-SOP가 `stage_order=6`이었던 문제 해결.

※ Stage는 마스터 데이터이며, 비용을 직접 소유하지 않는다.

**Stage Transition Legality Rules:**

* Stage Snapshot은 반드시 **직전 Stage Snapshot을 base_snapshot_id로 참조**해야 한다.
* Bid Snapshot은 base_snapshot_id가 NULL인 유일한 Snapshot이다.
* 설계원가 n차 Stage Snapshot은 n-1차 Stage Snapshot 없이 생성될 수 없다.
* Post-SOP Stage는 직전 Snapshot(SOP 또는 이전 Post-SOP)을 기준으로 순차 생성된다.

---

### 3.3 Snapshot

**Purpose:** 특정 Vehicle × Stage 시점의 비용 구조 고정

Key Fields:

* snapshot_id (PK)
* vehicle_id (FK → Vehicle)
* stage_code (FK → Stage)
* snapshot_type (BID | STAGE)
* base_snapshot_id (FK → Snapshot, nullable)
* created_at
* calculation_version
* reference_data_version

Constraints:

* (vehicle_id, snapshot_type=BID) UNIQUE — Vehicle당 Bid Snapshot은 하나만
* Snapshot은 생성 이후 UPDATE/DELETE 불가 — DB Trigger 강제 (10 §3.1)

---

### 3.4 CostComponent (통합 비용 마스터)

**Purpose:** 비용 항목의 개념, 의미, 계산 유형을 통합 정의

> **v1.3 변경:** v1.2에서 혼용되던 `CostItem` 명칭을 **`CostComponent`로 완전 통일**. 이후 문서에서 `CostItem`이라는 명칭은 사용하지 않는다.

Key Fields:

* component_code (PK) — 시스템 내부 식별자 (예: PRICE, MAT_UNIT, LABOR_RATE)
* component_name — 비용 항목 명칭
* component_type — A (Rate×Revenue) / B (Per-unit×Volume) / C (Program-level)
* semantic_type (INPUT | AGGREGATED | DERIVED)
* cost_category (PRICE | COST | METRIC)
* base_reference — 기준 (매출금액 / 대수 / 지정)
* default_rate — 기본 비율 (A-Type)
* default_included — 총비용 기본 포함 여부
* display_order
* is_active

**Semantic Type Definition:**

* INPUT: 사용자가 Stage별로 입력하는 원천 값 (판매가, 재료비, 조립비, 물류비, 포장비, 관세)
* AGGREGATED: INPUT 값을 집계하여 산출되는 값 (총매출, 총비용)
* DERIVED: 규칙 기반 계산으로 산출되는 지표 (총비용율, 제조원가율, 매출원가율)

※ AGGREGATED, DERIVED 값은 사용자 입력이 불가하다.

---

### 3.5 SnapshotCostValue

**Purpose:** Snapshot별 비용 값 저장 (차종 레벨 집계 결과)

Key Fields:

* id (PK)
* snapshot_id (FK → Snapshot)
* component_code (FK → CostComponent)
* per_unit_value — 대당 값 (Decimal)
* total_amount — 금액 합계 (Decimal)
* rate — 비율 (Decimal, A-Type용)

Constraints:

* (snapshot_id, component_code) UNIQUE

---

### 3.6 DerivedMetric

**Purpose:** 규칙 엔진에 의해 산출된 파생 지표

Key Fields:

* metric_code (PK)
* metric_name
* calculation_rule_version

※ 실제 값은 SnapshotCostValue로 저장된다.

### 3.7 ReferenceData

**Purpose:** 기준 데이터 (인건비, 환율 등)

Key Fields:

* id (PK)
* reference_type (LABOR | FX)
* region — 적용 지역 (생산지 기준)
* effective_year — 적용 연도
* currency — 통화 (FX type)
* value (Decimal)
* version — 데이터 버전
* status (PENDING | APPROVED)
* created_by / approved_by — 작성자/승인자
* created_at / approved_at

Constraints:

* (reference_type, region, effective_year, currency, version) UNIQUE

---

### 3.8 Part (품번)

**Purpose:** 차종 하위의 품번(Part Number) 단위 원가 관리

Key Fields:

* id (PK)
* vehicle_id (FK → Vehicle)
* part_number — 품번 코드 (String)
* part_name — 품명
* position_row — 행 위치 (FRT, RR1, RR2, RR3)
* position_side — 좌우 위치 (LH, RH, CTR)
* position_type — 부품 유형 (RTR, BKL, A, PT, H, ADJ, ECU, ETC)
* usage — 사용 수량 (Float)
* model_name — 적용 모델
* launch_region — 출시 지역
* currency — 통화 기준

Constraints:

* (vehicle_id, part_number) UNIQUE

---

### 3.9 PartCostValue (품번별 비용)

**Purpose:** 품번 × Snapshot별 상세 원가

Key Fields:

* id (PK)
* part_id (FK → Part)
* snapshot_id (FK → Snapshot)
* unit_price — 판매가
* material_cost — 재료비(부품가)
* assembly_cost — 조립비
* logistics_cost — 물류비
* packaging_cost — 포장비
* customs_cost — 관세

> **v1.3 변경:** `customs_cost` 필드 추가. 04 §4.4.2의 총비용 정의에 관세가 포함되므로 품번 레벨에서도 추적 필요.

※ 차종 서머리(SnapshotCostValue)는 PartCostValue의 집계(aggregation)로 산출된다. 집계 규칙은 04 §4.8 참조.

Constraints:

* (part_id, snapshot_id) UNIQUE
* Snapshot과 동일한 불변성 적용 (DB Trigger 차단)

---

## 4. Relationship Overview

```
Vehicle (1) ──── (N) Part                    ← 품번
Vehicle (1) ──── (N) VehicleVolume           ← 연도별 물량
Vehicle (1) ──── (N) Snapshot
Part    (1) ──── (N) PartCostValue           ← 품번별 Stage 비용
Stage   (1) ──── (N) Snapshot
Snapshot (1) ──── (N) SnapshotCostValue      ← 차종 서머리 (= 품번 집계)
Snapshot (1) ──── (N) PartCostValue           ← 품번별 비용 (불변)
Snapshot (1) ──── (N) EvaluationResult
CostComponent (Master) ──── (N) SnapshotCostValue
Snapshot (1) ──── (0..1) Snapshot (base_snapshot_id)
Target   (1) ──── (N) EvaluationResult
```

※ SnapshotCostValue(차종 서머리)는 PartCostValue(품번 상세)의 집계로 산출된다.

## 5. Bid vs Stage Comparison Mapping

* Bid Snapshot은 snapshot_type = BID 로 식별된다.
* Analysis 화면은 항상:

  * Bid Snapshot (Baseline Context)
  * Selected Stage Snapshot (Evaluation Context)
    를 동시에 조회한다.

모든 비교는 동일한 CostComponent 집합을 기준으로 수행되며,
Delta 계산은 **Calculation Engine 레벨에서 원자적으로 수행**된다.

> **v1.3 변경:** v1.2의 `CostItem` → `CostComponent`로 통일.

## 6. Data Integrity Rules

### 6.1 Snapshot Atomicity

* Snapshot 생성은 **원자적(Atomic)** 으로 처리된다.
* 하나라도 CostComponent 계산에 실패할 경우, Snapshot은 생성되지 않는다.
* 부분 Snapshot, 임시 Snapshot은 허용되지 않는다.
* 강제 수단: Validation Engine의 Snapshot Completeness 검증 (10 §4.4 참조)

### 6.2 Reference Data Binding

* Snapshot 생성 시 사용된 Reference Data는 다음 기준으로 고정된다.

  * reference_type
  * region
  * effective_year
  * currency
  * version
* Snapshot은 사용한 Reference Data 세트를 **명시적으로 참조**해야 한다.
* Reference Data 변경은 기존 Snapshot에 영향을 미치지 않는다.

> **v1.3 변경:** v1.2에서 잔존하던 `reference_code` / `reference_version` 참조 제거. 복합 키 구조로 통일.
