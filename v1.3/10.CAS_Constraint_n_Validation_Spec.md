# 10. CAS_Constraint_n_Validation_Spec

> **v1.3 신규 문서:** v1.2의 `10.CAS_Ontology_Specification`을 대체. OWL/SHACL/SWRL/Triple Store 기반 검증을 **DB 제약 + Validation Engine**으로 전환.

## 1. Document Purpose

CAS의 도메인 무결성을 **데이터베이스 레벨 제약**과 **애플리케이션 레벨 Validation Engine**의 이중 구조로 보장한다.

이 문서에서 정의하는 규칙은 다음 문서들의 원칙을 구현 수준에서 강제하기 위한 것이다.

* 01. CAS_Decision_n_Data_Immutability_Contract
* 03. CAS_Data_Model_n_Snapshot_Schema
* 04. CAS_Calculation_Engine_n_Cost_Rule_Spec
* 05. CAS_Target_n_Evaluation_Logic_Spec

---

## 2. Architecture

### 2.1 Two-layer Enforcement

```
[API Request]
  └─ Validation Engine (Application Layer)
       ├─ Input Validation
       ├─ Stage Transition Validation
       ├─ Snapshot Completeness Validation
       ├─ Aggregation Consistency Validation
       └─ Bid Non-evaluable Validation
  └─ PostgreSQL (Database Layer)
       ├─ FK Constraints
       ├─ CHECK Constraints
       ├─ UNIQUE Constraints
       └─ Immutability Triggers
```

### 2.2 Validation 실행 시점

| 시점 | 검증 주체 | 검증 내용 |
|------|----------|----------|
| Snapshot 생성 전 | Validation Engine | Input, Stage Transition, Completeness |
| Snapshot 생성 중 | Calculation Engine | 계산 무결성, 집계 정합성 |
| Snapshot 생성 후 | DB Trigger | 불변성 (UPDATE/DELETE 차단) |
| 상시 | DB Constraints | FK, CHECK, UNIQUE |

### 2.3 Validation 실패 시 동작

* Validation Engine 검증 실패 → API가 에러 응답 반환, Snapshot 생성 중단
* DB Constraint 위반 → 트랜잭션 롤백, 에러 로그 기록
* 두 레이어의 검증이 모두 통과해야만 Snapshot이 확정된다

## 3. Database-level Constraints

### 3.1 Snapshot Immutability Trigger

**Purpose:** 생성 완료된 Snapshot의 모든 값 수정을 차단한다 (01 §2.2 강제).

```sql
-- Snapshot 테이블 UPDATE/DELETE 차단
CREATE OR REPLACE FUNCTION prevent_snapshot_modification()
RETURNS TRIGGER AS $$
BEGIN
  RAISE EXCEPTION 'Snapshot은 생성 이후 수정·삭제가 불가합니다. snapshot_id: %', OLD.snapshot_id;
  RETURN NULL;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_snapshot_immutable
  BEFORE UPDATE OR DELETE ON snapshots
  FOR EACH ROW
  EXECUTE FUNCTION prevent_snapshot_modification();

-- SnapshotCostValue 테이블도 동일 적용
CREATE TRIGGER trg_snapshot_cost_value_immutable
  BEFORE UPDATE OR DELETE ON snapshot_cost_values
  FOR EACH ROW
  EXECUTE FUNCTION prevent_snapshot_modification();

-- PartCostValue 테이블도 동일 적용
CREATE TRIGGER trg_part_cost_value_immutable
  BEFORE UPDATE OR DELETE ON part_cost_values
  FOR EACH ROW
  EXECUTE FUNCTION prevent_snapshot_modification();

-- EvaluationResult 테이블도 동일 적용
CREATE TRIGGER trg_evaluation_result_immutable
  BEFORE UPDATE OR DELETE ON evaluation_results
  FOR EACH ROW
  EXECUTE FUNCTION prevent_snapshot_modification();
```

### 3.2 Bid Snapshot Uniqueness Constraint

## 4. Application-level Validation Engine

Validation Engine은 순수 함수로 구현되며, Snapshot 생성 전에 실행된다.

### 4.1 Snapshot Immutability Validation

**Rule:** 이미 존재하는 Snapshot의 ID로 새 데이터를 생성하려는 시도를 차단한다.

```typescript
function validateSnapshotNotExists(snapshotId: string): ValidationResult {
  // 이미 존재하는 snapshot_id로 생성 시도 시 에러
}
```

**Error Code:** `SNAPSHOT_ALREADY_EXISTS`

---

### 4.2 Stage Transition Validation

**Rule:** Stage Snapshot은 반드시 직전 Stage의 Snapshot이 존재해야 생성 가능하다 (03 §3.2).

```typescript
function validateStageTransition(
  vehicleId: string,
  targetStageCode: string,
  existingSnapshots: Snapshot[]
): ValidationResult {
  // 1. Bid Snapshot은 base_snapshot_id가 NULL인 유일한 Snapshot
  // 2. DC1은 BID Snapshot이 있어야 생성 가능
  // 3. DC2는 DC1 Snapshot이 있어야 생성 가능
  // 4. DC3은 DC2 Snapshot이 있어야 생성 가능
  // 5. SOP는 DC3(또는 존재하는 마지막 DC) Snapshot이 있어야 생성 가능
  // 6. POST_SOP_N은 직전 Snapshot(SOP 또는 POST_SOP_N-1)이 있어야 생성 가능
}
```

**Error Codes:**
* `STAGE_PREVIOUS_REQUIRED` — 직전 Stage Snapshot 미존재
* `BASE_SNAPSHOT_INVALID` — base_snapshot_id 참조 오류
* `BID_ALREADY_EXISTS` — Bid Snapshot 중복 생성 시도

---

### 4.3 Input Validation

**Rule:** INPUT CostComponent의 무결성 규칙을 검증한다 (04 §6.1).

```typescript
function validateInputCosts(costs: InputCosts): ValidationResult {
  // 1. 모든 필수 INPUT 항목이 존재하는지 (NULL 불가)
  // 2. 음수 값이 없는지 (CASHBACK, DEV_REC 제외)
  // 3. 판매가(PRICE)가 0보다 큰지
  // 4. 관세(CUSTOMS)가 0 이상인지
}
```

**Error Codes:**
* `INPUT_NULL` — 필수 항목 누락
* `INPUT_NEGATIVE` — 허용되지 않는 음수 값
* `PRICE_ZERO` — 판매가가 0 이하

```typescript

```

## 5. Validation Error Response Format

모든 Validation 에러는 다음 형식으로 API에 반환된다.

```json
{
  "errorCode": "STAGE_PREVIOUS_REQUIRED",
  "message": "설계원가 2차는 설계원가 1차 Snapshot 없이 생성할 수 없습니다.",
  "context": {
    "vehicleId": "UUID",
    "stageCode": "DC2",
    "requiredStage": "DC1"
  },
  "timestamp": "2024-01-15T10:30:00.000Z"
}
```

## 6. Validation Engine 구현 원칙

### 6.1 순수 함수

* 모든 Validation 함수는 **순수 함수**로 구현한다.
* DB 접근은 Validation 함수 외부에서 수행하고, 결과만 인자로 전달한다.

### 6.2 테스트 가능성

* 모든 Validation 규칙은 08-A 불변식 테스트에 대응한다.
* Validation Engine의 모든 분기는 Unit Test로 커버한다.

### 6.3 에러 집계

* 하나의 Snapshot 생성 요청에서 복수의 Validation 에러가 발생할 수 있다.
* 모든 에러를 집계하여 한 번에 반환한다 (fail-fast가 아닌 **collect-all** 전략).

---

## 7. 변경 시 주의

Validation 규칙을 바꾸면 01, 03, 04, 05, 08-A 문서와 맞는지 반드시 확인한다. Validation 규칙 추가·변경은 대응하는 08-A 불변식 테스트와 반드시 함께 업데이트해야 한다.
