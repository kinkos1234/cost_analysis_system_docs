# 08-B. CAS_Calculation_Engine_Unit_n_Property_Test_Spec

## 1. Purpose

계산 엔진(04문서)과 비용 사전(Catalog)을 **Unit/Property 기반 TDD**로 검증하기 위한 테스트 규격(L1/L2)이다.

아래 문서를 테스트로 검증한다.

* 04. CAS_Calculation_Engine_n_Cost_Rule_Spec
* 05. CAS_Target_n_Evaluation_Logic_Spec (평가 입력값 전제 검증)
* 08-A. CAS_Domain_Invariant_Test_Spec (불변식 준수)

---

## 2. Test Levels & Conventions

### 2.1 Levels

* **L1 Unit Tests:** Pure function 단위(입력→출력) 테스트
* **L2 Property Tests:** 입력 범위를 확장해 성질(항상 참)을 검증
* **L3 Ontology Parity Tests:** SWRL 추론 결과와 계산 엔진 결과의 일치성 검증

### 2.2 Notation

* per-unit 값은 소수/정수 모두 허용
* 금액(amount)은 원 단위 integer로 표현(부동소수점 금지)
* 5Y 평균은 단순 평균(AVERAGE)

---

## 3. Calculation Unit Tests (L1)

### 3.1 Standard Aggregation (per-unit)

#### UT-CALC-001: TotalCost(per-unit)

**Given** M=60, A=10, L=5, K=2
**When** total_cost = M+A+L+K
**Then** total_cost = 77

#### UT-CALC-002: TotalRevenue(per-unit)

**Given** PRICE=100
**Then** total_revenue = 100

#### UT-CALC-003: CostRatio(per-unit)

**Given** total_cost=77, total_revenue=100
**Then** cost_ratio = 0.77

---

### 3.2 Amount Conversion (yearly)

#### UT-AMT-001: RevenueAmount(year)

**Given** price_per_unit[Y1]=100, volume[Y1]=10,000
**Then** revenue_amount[Y1] = 1,000,000

#### UT-AMT-002: CostAmount(year)

**Given** mat_per_unit[Y1]=60, volume[Y1]=10,000
**Then** mat_amount[Y1] = 600,000

#### UT-AMT-003: TotalRevenue(amount)

**Given** revenue_amount[Y1..Y5]
**Then** total_revenue_amount = SUM(revenue_amount[Y1..Y5])

#### UT-AMT-004: TotalCost(amount)

**Given** selected_cost_component_amounts[year]
**Then** total_cost_amount = SUM(cost_amounts[year]) aggregated across years

---

### 3.3 5Y Average View (per-unit)

#### UT-AVG5-001: Avg5(price)

**Given** price[Y1..Y5] = [100, 100, 90, 90, 80]
**Then** avg5_price = AVERAGE = 92

#### UT-AVG5-002: Avg5(cost item)

**Given** mat[Y1..Y5] = [60, 61, 62, 63, 64]
**Then** avg5_mat = 62

---

### 3.4 Extended Catalog Components

#### UT-EXT-A-001: A-Type Rate×Revenue

**Given** rate=0.05, revenue_amount[Y1]=10,000,000
**Then** component_amount[Y1] = 500,000

#### UT-EXT-B-001: B-Type per-unit×Volume

**Given** per_unit=77, volume[Y1]=10,000
**Then** component_amount[Y1] = 770,000

#### UT-EXT-C-001: C-Type Allocation required

**Given** component_type=C and included=ON and allocation missing
**Then** error_code = PROGRAM_ALLOCATION_MISSING

#### UT-EXT-C-002: C-Type Allocation applied

**Given** allocation[Y1..Y5] provided
**Then** component_amount[year] = allocation[year]

---

### 3.5 Rounding & Precision

#### UT-ROUND-001: CostRatio precision

**Rule:** CAS v1은 CostRatio를 내부적으로 high precision(decimal)로 유지하고, UI 출력 시 4자리 반올림 표준을 사용한다.
**Given** total_cost=1, total_revenue=3
**Then** internal=0.333333..., display=0.3333

---

## 4. Property Tests (L2)

### 4.1 Domain Range Properties

#### PT-RANGE-001: Core costs non-negative

**For all** M,A,L,K in [0..MAX]
**Then** total_cost >= 0

#### PT-RANGE-002: Revenue positive

**For all** PRICE in (0..MAX]
**Then** total_revenue > 0

---

### 4.2 Algebraic Properties

#### PT-ALG-001: Additivity

**For all** M1,M2,A,L,K
**Then** total_cost(M1+M2,A,L,K) = total_cost(M1,A,L,K)+M2

#### PT-ALG-002: Ratio monotonicity (holding revenue)

**For all** revenue fixed, cost increases
**Then** cost_ratio increases

---

### 4.3 View Properties

#### PT-VIEW-001: View switch purity

**Given** 동일 Snapshot
**When** compute INIT vs AVG5
**Then** INIT 계산 결과는 AVG5 계산 과정에 의해 변경되지 않는다

#### PT-VIEW-002: Avg5 bounds

**For all** values v1..v5
**Then** min(v) ≤ avg(v) ≤ max(v)

---

### 4.4 Negative-allowed Component Properties

#### PT-NEG-001: Cashback negativity allowed

**Given** CASHBACK included and value < 0
**Then** total_cost_amount may decrease but must still satisfy INV-CALC-002 (ratio definition)

---

### 4.5 Overflow / Large Number Properties

#### PT-OVF-001: Integer amount safety

**For all** price_per_unit, volume within configured bounds
**Then** revenue_amount multiplication does not overflow 64-bit integer (or system uses bigint)

---

## 5. Test Data Generation (Fuzz)

* Generate random per-unit costs in [0..1e6]
* Generate random volumes in [0..1e7]
* Generate rates in [0..1]
* Randomly toggle optional components(OFF/ON) with required allocation generation for Type C

All generated cases must satisfy:

* No NULLs
* PRICE > 0

---

## 6. Ontology Parity Tests (L3)

> L3 테스트는 계산 엔진의 결과와 SWRL 추론 결과가 **모든 경우에 일치**함을 검증한다.
> 불일치는 BLOCKER 결함으로 처리한다 (08-A INV-ONTO-002, 10 §10 참조).

### 6.1 Calculation Parity

#### OT-CALC-001: TotalCost Parity

**Given** Snapshot S with known input costs
**When** 계산 엔진과 SWRL-CALC-002 각각 TotalCost 산출
**Then** calcEngine.totalCost(S) = swrl.totalCost(S)

#### OT-CALC-002: CostRatio Parity

**Given** Snapshot S with known input costs and revenue
**When** 계산 엔진과 SWRL-CALC-003 각각 CostRatio 산출
**Then** calcEngine.costRatio(S) = swrl.costRatio(S)

---

### 6.2 Evaluation Parity

#### OT-EVAL-001: Evaluation Status Parity

**Given** Snapshot S, View V, Target T
**When** 계산 엔진 평가 로직과 SWRL-EVAL-001~003 각각 Status 판정
**Then** calcEngine.evaluationStatus(S, V) = swrl.evaluationStatus(S, V)

---

### 6.3 SHACL Constraint Tests

#### OT-SHACL-001: Snapshot Immutability Enforcement

**Given** 유효한 Snapshot S가 Triple Store에 존재
**When** S의 트리플을 수정 시도
**Then** SHACL `cas:SnapshotImmutabilityShape` 검증 실패

#### OT-SHACL-002: Stage Transition Enforcement

**Given** Stage N의 Snapshot이 존재하지 않음
**When** Stage N+1의 Snapshot 생성 시도
**Then** SHACL `cas:StageTransitionShape` 검증 실패

---

## 7. Exit Criteria

* 모든 L1 Unit Test 통과
* L2 Property Test 최소 10,000 case fuzz 통과
* L3 Ontology Parity Test 100% 일치 (계산 엔진 = SWRL 추론)
* 불변식(08-A) 위반 0건

위 Exit Criteria를 전부 통과해야 계산 엔진의 정확성과 안전성이 확보된 것으로 본다.
