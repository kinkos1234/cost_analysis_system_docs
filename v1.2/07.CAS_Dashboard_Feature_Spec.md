# 07. CAS_Dashboard_Feature_Spec

## 1. Document Purpose

CAS Dashboard는 관리 화면이 아니라 **리스크 감시 화면**이다.

여기서 계산이나 판단을 새로 하지 않는다. 이미 확정된 Snapshot·Evaluation 결과를 보여주되, **어디가 문제인지 바로 눈에 들어오게** 만드는 것이 목적이다.

아래 문서들의 결과를 화면으로 표현한다.

* 02. CAS_Information_Architecture
* 05. CAS_Target_n_Evaluation_Logic_Spec
* 06. CAS_API_Specification
* 08-A / 08-B CAS_Test_Specifications

---

## 2. Dashboard Design Axioms

### 2.1 Decision Latency Minimization

* 사용자가 Dashboard를 보고 **3초 이내에 ‘문제 차종이 있는지’ 판단**할 수 있어야 한다.
* 세부 수치 확인은 Dashboard의 책임이 아니다.

### 2.2 Result-only Surface

* Dashboard는 **결과만 노출**한다.
* 원인 분석, 계산 근거, 수정 행위는 하위 화면으로 위임한다.

### 2.3 Global Context Consistency

* Dashboard에 표시되는 모든 정보는 **동일한 View(INIT/AVG5)** 와 동일한 Snapshot 맥락을 공유해야 한다.

---

## 3. Global Controls

### 3.1 View Selector (Global, Mandatory)

| Option | Meaning          |
| ------ | ---------------- |
| INIT   | 초기년 기준 평가 View   |
| AVG5   | 5년 평균 기준 평가 View |

Rules:

* View 변경 시 Dashboard 전체가 재평가된 것처럼 보이면 안 된다.
* **이미 있는 Evaluation 결과를 다른 View로 보는 것**일 뿐이라는 점이 UI에서 분명히 드러나야 한다.

---

## 4. Core Dashboard Zones

### 4.1 Portfolio Risk Overview (Top Priority)

**Purpose:** 조직 차원의 리스크 존재 여부를 즉시 파악

Displayed Metrics:

* 전체 Vehicle 수
* RED / YELLOW / GREEN / EXCLUDED 분포

Data Source: Portfolio 수준 집계 데이터는 SPARQL 집계 쿼리 또는 동등한 관계형 쿼리를 통해 산출될 수 있으며, 두 경로의 결과는 동일해야 한다 (10 §10 참조).

Rules:

* RED는 항상 최상단, 최대 시각 강조
* EXCLUDED(Bid 등)는 별도 그룹으로 분리

---

### 4.2 Critical Vehicle List

**Purpose:** 즉시 조치가 필요한 차종 식별

Inclusion Rules:

* 현재 Stage Evaluation = RED
* 또는 YELLOW 이면서 직전 Stage 대비 악화

Displayed Fields:

* Vehicle Name
* Current Stage
* Evaluation Status
* Target 대비 핵심 Delta 요약

Data Source: Critical Vehicle 목록은 `cas:EvaluationResult`의 `cas:evaluationStatus`가 RED인 개체를 온톨로지 쿼리 또는 동등한 관계형 쿼리로 추출한다.

Interaction:

* 클릭 시 해당 Vehicle의 Analysis 화면으로 이동

---

### 4.3 Stage Pressure Map

**Purpose:** 문제가 특정 Stage에 집중되어 있는지 파악

Display:

* Stage × Vehicle Count 매트릭스 또는 Bar

Rules:

* Stage 순서는 고정
* 비정상 Stage(Post-SOP 반복 등)는 시각적으로 구분

---

### 4.4 Recent Decision Events

**Purpose:** 최근 의사결정 활동 모니터링

Displayed Fields:

* Vehicle Name
* Stage
* Snapshot 생성 시각

Rules:

* 시간 역순 정렬
* 수정/삭제/재계산 UI 제공 금지

---

## 5. Visual Emphasis Rules

### 5.1 Status Semantics

| Status   | Visual Meaning |
| -------- | -------------- |
| GREEN    | 안정 상태          |
| YELLOW   | 주의 필요          |
| RED      | 즉각 개입 필요       |
| EXCLUDED | 판단 대상 아님       |

Rules:

* 색상은 보조 수단이며, 아이콘/텍스트 병행 필수
* RED 상태는 단일 화면 내 2회 이상 반복 강조 금지(피로 방지)

---

## 6. Interaction & Navigation Constraints

### 6.1 Read-only Guarantee

* Dashboard에서는 어떠한 데이터 변경도 불가능하다.
* 수정 가능해 보이는 UI 요소 자체를 배제한다.

---

### 6.2 Deterministic Drill-down

* Drill-down은 항상 **동일 Vehicle·Stage·View** Context를 유지한다.
* Back Navigation 시 Context 손실은 결함으로 간주한다.

---

## 7. Role Neutrality

* Dashboard는 모든 Role(Admin/Manager/Staff/Viewer)에 대해 동일하게 동작한다.
* 권한에 따른 정보 숨김은 허용되지 않는다.

---

## 8. Forbidden Dashboard Patterns

다음 패턴은 설계 위반으로 간주한다.

* Dashboard에서 계산 수치 직접 수정
* 복수 기준(View) 동시 표시
* 사용자가 기준을 선택해야만 상태를 이해할 수 있는 구조
* Snapshot 재생성 또는 재평가 버튼
* SPARQL 쿼리 인터페이스 또는 Raw 트리플 데이터의 사용자 직접 노출

---

## 9. Test Alignment

Dashboard 구현은 다음 테스트 조건을 충족해야 한다.

* View 전환 시 상태 불일치 없음
* Bid 기준 차량의 평가 미수행 표시 정확성
* RED/YELLOW 판단 기준의 재현성
