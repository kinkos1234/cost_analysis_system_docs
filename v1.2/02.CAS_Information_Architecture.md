# 02. CAS_Information_Architecture

## 1. Document Purpose

01문서에서 정한 결정권한·불변성 원칙이 실제 화면에서도 지켜지도록, 정보 구조(IA)를 설계한다.

CAS IA의 우선순위는 편의성보다 **판단 오류 방지, 책임 경계 구분, 시간 맥락 고정**이다.

---

## 2. IA Design Principles

### 2.1 Stage-Centric Navigation

* CAS의 모든 주요 화면은 **Stage(Stage Event)**를 중심으로 구성된다.
* 연차(Year)는 분석 축으로만 사용되며, 기본 탐색 축이 될 수 없다.

### 2.2 Read-Only by Default

* Snapshot이 생성된 이후의 모든 데이터는 **기본적으로 읽기 전용(Read-only)**으로 표시된다.
* 수정 가능한 영역은 눈에 띄게 구분해서 표시한다.

### 2.3 Context Preservation

* 사용자는 지금 보고 있는 데이터가 **어떤 Stage, 어떤 Snapshot 시점**인지 항상 알 수 있어야 한다.
* 어떠한 화면에서도 Stage Context가 숨겨지면 안 된다.

## 4. Core IA Entities

### 4.1 Vehicle (차종)

* CAS의 최상위 분석 단위
* 모든 데이터는 반드시 특정 Vehicle Context 하에 존재
* 온톨로지 정체성: `cas:Vehicle` 클래스 (10 §3 참조)

### 4.2 Stage (비용 결정 단계)

* Vehicle 하위의 **시간적·의사결정 이벤트 단위**
* Stage는 선형적 흐름을 가지되, Post-SOP Stage는 비정형 반복을 허용
* 온톨로지 정체성: `cas:Stage` 클래스, 각 Stage는 OWL Named Individual로 정의 (10 §5.1 참조)

### 4.3 Snapshot

* Stage 진입 시 자동 생성되는 불변 데이터 묶음
* 분석·비교·리포트는 전부 Snapshot 기준으로 동작
* 온톨로지: `cas:Snapshot` 클래스, SHACL `cas:SnapshotImmutabilityShape`로 불변성 보호 (10 §6.1 참조)

## 5. Page-level Information Structure

### 5.1 Dashboard

**목적:** 전체 차량 포트폴리오의 상태 요약

* 전체 Vehicle 수
* 현재 Stage 분포
* 목표 미달성 Vehicle 수
* 최근 생성된 Snapshot 목록

※ Dashboard는 **요약 정보만 제공**하며, 데이터 수정 기능은 제공하지 않는다.

---

### 5.2 Vehicles List

**목적:** Vehicle 탐색 및 Stage 접근

* Vehicle 기본 정보
* 현재 진행 중 Stage
* 최근 Snapshot 시점

Interaction:

* Vehicle 클릭 → Vehicle Detail Page 이동

---

### 5.3 Vehicle Detail

**목적:** 특정 Vehicle의 Stage 흐름 파악

구성:

* Vehicle Overview
* Stage Timeline (Bid → Design Cost → SOP → Post-SOP)
* 각 Stage별 Snapshot 접근 링크

※ Stage Timeline은 **순서 고정**이며, 임의 재정렬 불가

---

### 5.4 Stage Snapshot View

**목적:** 특정 Stage의 비용 구조 및 평가 결과 확인

구성:

* Snapshot Metadata (Stage, 생성 시점, 기준 데이터 버전)
* 비용 Breakdown (Read-only)
* Derived Metrics
* Target Evaluation Result
* Interpretation (Comment 영역)

※ 비용 수치 및 평가 결과는 수정 불가

---

### 5.5 Analysis

**목적:** 수주 시점(Bid) 대비 현재 Stage까지의 비용 구조 변화 비교

이 페이지의 목적은 하나다: 특정 Vehicle의 **수주(Bid) 시점 비용 구조와 현재 Stage 비용 구조를 나란히 비교**하는 것. "단계별 추이"를 보여주는 게 아니라, **수주가 대비 지금 얼마나 바뀌었는지**를 바로 보게 하려는 것이다.

---

#### 비교 원칙

* 비교의 기준은 항상 **Bid Snapshot(수주가)** 이다.
* Bid Snapshot은 테이블의 **좌측 기준 블록**으로 고정된다.
* 비교 대상은 **선택된 Stage(예: 설계원가 2차)** 이며, 중간 Stage는 선택적으로 참조만 가능하다.
* 하나의 Analysis 화면은 **하나의 Vehicle + 하나의 비교 Stage**만을 다룬다.

---

#### Table Structure (Required)

```
| 차종명 | 수주가(Bid)                                   | 단계별 가격(Current Stage)                     |
|        | 판매가 | 재료비 | 조립비 | 물류비 | 포장비 | 총매출 | 총비용 | 총비용율 | 단계 | 판매가 | 재료비 | 조립비 | 물류비 | 포장비 | 총매출 | 총비용 | 총비용율 |
```

* 좌측 블록은 **항상 Bid Snapshot 기준 값**이다.
* 우측 블록은 **사용자가 선택한 단일 Stage Snapshot** 기준 값이다.
* Stage 컬럼에는 비교 대상 Stage 명칭(예: 설계원가 2차)이 명시된다.

---

#### UI/UX Enforcement Rules

* Bid 영역과 Stage 영역은 **시각적으로 확실히 구분되는 컬럼 그룹**으로 표시한다.
* Bid 영역은 항상 기준(anchor)으로 인식될 수 있도록 **배경 또는 구분선**을 사용한다.
* 두 영역의 비용 항목 순서와 항목명은 **완전히 동일**해야 한다.
* 사용자는 Bid 영역의 데이터를 접거나 숨길 수 없다.

---

#### Data Constraints

* 본 Analysis 화면은 **오직 Snapshot 데이터만 사용**한다.
* Bid Snapshot은 항상 해당 Vehicle의 최초 Snapshot으로 고정된다.
* 비교 Stage Snapshot은 **현재 진행 중이거나, 사용자가 명시적으로 선택한 Stage**만 허용된다.
* Live 데이터, 임시 계산 결과, 가중치 시뮬레이션은 허용되지 않는다.

※ 본 화면은 ‘시계열 분석’이 아니라, **의사결정 기준 대비 현재 상태를 확인하는 판단용 비교 화면**이다.

---

### 5.6 Reports

**목적:** 공식 리포트 확인 및 발송 이력 관리

* 목표 미달성 Vehicle 목록
* 발송 이력
* 리포트 상태 (Sent / Pending)

---

### 5.7 Reference Data

**목적:** 기준 데이터 관리

* 인건비 기준 데이터
* 환율 기준 데이터

권한:

* Staff: 입력/수정 요청
* Manager: 승인

※ 승인 전 데이터는 **Pending 상태**로 표시

---

### 5.8 Admin

**목적:** 시스템 운영 관리

* 사용자 관리
* 권한 관리
* 시스템 설정

---

## 6. Forbidden IA Patterns

아래 패턴은 CAS에서 쓰면 안 된다.

* Stage Context 없이 데이터 표시
* Snapshot이 아닌 Live 데이터 비교
* Derived Metric 직접 편집 UI
* Stage Timeline 임의 수정
* Raw 온톨로지 트리플 또는 SPARQL 쿼리 인터페이스의 최종 사용자 직접 노출

---

## 7. 변경 시 주의

IA를 바꾸려면 00·01 문서와 맞는지 먼저 확인한다. UI·API·권한 설계는 이 IA를 기준으로 한다.
