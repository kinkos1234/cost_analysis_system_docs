# 06. CAS_API_Specification

## 1. Document Purpose

CAS의 API를 정의한다. 모든 API는 08-A, 08-B 테스트를 통과해야 하고, 00~05문서의 원칙을 지켜야 한다.

구체적으로:

* 08-A, 08-B 테스트를 전부 통과할 것
* Snapshot 불변성, Stage 전환 합법성, View 일관성을 API 레벨에서 지킬 것

---

## 2. API Design Principles

### 2.1 Contract-first API

* API가 **직접 판단하는 건 없다.** 계산·평가 결과를 생성·고정·조회하는 전달자(Transport Layer)일 뿐이다.
* 계산·평가 로직은 API 바깥의 Domain Layer 책임이다.
* API는 UI 편의가 아니라 **설계 계약 집행**을 목적으로 한다.
* API는 계산/평가 결과를 수정할 수 없다.

### 2.2 Lifecycle-consistent API

* Snapshot → Calculation → Evaluation Lifecycle은 **단방향·불가역적**이다.
* API로 Lifecycle을 변경하거나, 재실행하거나, 일부만 돌릴 수 없다.

### 2.4 Ontology-Aware Query Support

* 온톨로지 기반 쿼리(SPARQL)는 **API 수준에서만 제공**되며, 최종 사용자에게 직접 노출되지 않는다.
* 온톨로지 쿼리 결과는 관계형 DB 조회와 **의미적으로 동등**해야 한다.
* SPARQL 엔드포인트는 **읽기 전용**이며, Triple Store의 직접 수정은 불가하다.

---

### 2.3 Context-explicit Requests

* 모든 요청은 필요한 Context를 명시해야 하며,
* Context가 불필요한 API는 **불필요한 Context를 요구하지 않는 것이 원칙**이다.

| Context    | Required    | Description             |
| ---------- | ----------- | ----------------------- |
| vehicle_id | Yes         | 차종 식별자                  |
| stage_code | Conditional | Stage Context (조회/생성 시) |
| view_code  | Conditional | INIT / AVG5 (분석/평가 시)   |

---

### 2.5 Naming Convention — v1.1 구현 반영

> API의 request/response 필드명은 **camelCase**를 표준으로 한다 (JavaScript/TypeScript 네이밍 컨벤션).
> 본 문서의 예시에서 `snake_case`로 기술된 필드는 실제 구현 시 camelCase로 변환된다.
>
> 예: `vehicle_id` → `vehicleId`, `stage_code` → `stageCode`, `base_snapshot_id` → `baseSnapshotId`

---

## 3. Error Contract (Global)

> Error는 API가 생성하는 것이 아니라 **Domain Rule Engine의 판단 결과를 전달**한다.
> API Error는 Transport 오류(인증, 권한, 형식)에 한정된다.

```json
{
  "error_code": "STAGE_PREVIOUS_REQUIRED",
  "message": "설계원가 2차는 설계원가 1차 Snapshot 없이 생성할 수 없습니다.",
  "context": {
    "vehicleId": "V-A",
    "stageCode": "DC2"
  },
  "timestamp": "2024-01-15T10:30:00.000Z"
}
```

> **v1.1 구현 반영:** Error 형식을 `{ error_code, message, context?, timestamp }` 구조로 통일. `timestamp`는 ISO 8601 형식.

## 4. Snapshot APIs

> Snapshot 생성 시점에 **Calculation과 Evaluation(INIT/AVG5)** 이 동시에 수행되고 고정된다.
> 이후 어떠한 API 호출도 Calculation/Evaluation을 재실행할 수 없다.

### 4.1 Create Snapshot

**POST** `/api/snapshots`

**Purpose:** Stage Snapshot 생성 (Atomic)

**Request Body:**

```json
{
  "vehicleId": "UUID",
  "stageCode": "DC1",
  "vehicleCost": {
    "unitPrice": 100,
    "materialCost": 60,
    "assemblyCost": 10,
    "logisticsCost": 5,
    "packagingCost": 2
  },
  "partCosts": [],
  "rateOverrides": {}
}
```

> **v1.1 구현 반영:** `base_snapshot_id`는 서비스 레이어에서 자동 결정(직전 Stage Snapshot). `input_costs` flat map은 구조화된 `vehicleCost` / `partCosts`로 분리. `rateOverrides`로 A-Type 비율 재정의 가능.

**Rules Enforced:**

* Stage Transition Legality (03 §3.2)
* Calculation Engine Rules (04)
* Snapshot Atomicity (01, 03)
* SHACL Constraint Validation: `cas:StageTransitionShape`, `cas:SnapshotAtomicityShape`, `cas:InputValidationShape` (10 §6)
* SWRL Inference Execution: 계산 규칙(SWRL-CALC-001~003) + 평가 규칙(SWRL-EVAL-001~003) 자동 추론 (10 §7)
* Triple Store Sync: Snapshot 생성 시 PostgreSQL 커밋과 Triple Store 동기화가 **원자적으로 수행**되어야 한다 (10 §2.3)

**Success (201):**

```json
{
  "snapshotId": "UUID",
  "evaluationSummary": {
    "totalTargets": 4,
    "green": 3,
    "yellow": 1,
    "red": 0,
    "requiresReport": false
  }
}
```

> **v1.1 구현 반영:** 응답에 평가 요약(evaluationSummary) 포함. `calculation_version`은 Snapshot 상세 조회 시 반환.
```

**Failure Cases:**

* INPUT_NULL / INPUT_NEGATIVE / PRICE_ZERO
* STAGE_PREVIOUS_REQUIRED / BASE_SNAPSHOT_INVALID

---

### 4.2 Get Snapshot (Read-only)

**GET** `/api/snapshots/{snapshot_id}`

**Rules:**

* Snapshot 수정/삭제 API는 제공되지 않는다.

## 5. Analysis APIs

### 5.1 Get Analysis Table (Bid vs Stage)

**GET** `/api/analysis`

**Query Params:**

* vehicleId (optional) — 차종의 모든 Snapshot 분석 데이터 조회
* snapshotId (optional) — 특정 Snapshot 분석 데이터 조회

> **v1.1 구현 반영:** `vehicleId` 또는 `snapshotId` 중 하나 이상 필수. `stage_code`, `view_code`는 응답에 포함되며 요청 파라미터로는 사용하지 않음.

**Response:**

```json
{
  "vehicleId": "UUID",
  "snapshotCount": 3,
  "snapshots": [
    {
      "snapshotId": "UUID",
      "stageCode": "DC1",
      "snapshotType": "STAGE",
      "calculationVersion": "1.0.0",
      "costComponents": { "PRICE": { "perUnitValue": "100000", "totalAmount": "..." } },
      "partCosts": [],
      "evaluations": [{ "viewCode": "INIT", "metricCode": "COST_RATIO", "status": "GREEN" }]
    }
  ]
}
```

**Rules Enforced:**

* Bid Anchor 고정 (02 §5.5)
* View Context Consistency (05)

## 6. Evaluation APIs

> Evaluation은 Snapshot 생성 시 이미 확정된 결과를 **조회(fetch)** 하는 개념이다.
> API는 Evaluation을 실행(run)하지 않는다.

### 6.1 Get Evaluation Result

**GET** `/api/evaluations`

**Query Params:**

* vehicleId (required) — 차종별 최신 Snapshot의 평가 결과 요약

> **v1.1 구현 반영:** `vehicleId` 기반 요약 조회로 변경. 상세 평가 결과는 Analysis API 응답의 `evaluations` 필드에 포함됨.

**Response:**

```json
{
  "snapshotId": "UUID",
  "stageCode": "DC1",
  "results": [
    {
      "targetId": "UUID",
      "viewCode": "INIT",
      "metricCode": "COST_OF_SALES_RATIO",
      "metricValue": "0.78",
      "targetValue": "0.80",
      "status": "GREEN"
    }
  ],
  "summary": {
    "total": 4,
    "green": 3,
    "yellow": 1,
    "red": 0,
    "requiresReport": true
  }
}
```

**Rules Enforced:**

* View-dependent Evaluation (05)
* Target immutability

**Failure:**

* SNAPSHOT_NOT_FOUND — 해당 차종에 Snapshot이 없는 경우

### 7.4 Update Target (Manager only)

**PATCH** `/api/targets/{id}`

**POST** `/api/targets/defaults`

**Request Body:**

```json

  "vehicleId": "UUID"

```

## 10. Ontology Query APIs

> 온톨로지 쿼리 API는 Triple Store에 대한 **읽기 전용 인터페이스**를 제공한다.
> 최종 사용자에게 직접 노출되지 않으며, 내부 시스템 통합 및 관리 목적으로만 사용된다.

### 10.1 SPARQL Query

**POST** `/api/ontology/sparql`

**Request Body:**

```json
{
  "query": "SELECT ?vehicle ?status WHERE { ?vehicle cas:evaluationStatus ?status }",
  "format": "json"
}
```

**Rules:**

* SELECT 쿼리만 허용 (INSERT/UPDATE/DELETE 차단)
* 쿼리 결과는 지정된 포맷(JSON-LD, Turtle, JSON)으로 반환
* 쿼리 타임아웃 제한 적용

### 10.2 Get Ontology Classes

**GET** `/api/ontology/classes`

**Purpose:** 현재 온톨로지 스키마의 클래스 계층 구조 조회

### 10.3 Get Ontology Version

**GET** `/api/ontology/version`

**Purpose:** 현재 적용된 온톨로지 스키마 버전 정보 조회

### 10.4 Sync Triple Store (Admin only)

**POST** `/api/ontology/sync`

**Purpose:** PostgreSQL 데이터를 Triple Store로 동기화

**Request Body:**

```json
{
  "scope": "full" | "masterData" | "vehicle" | "snapshot",
  "vehicleId": "UUID",
  "snapshotId": "UUID"
}
```

### 10.5 Validate SHACL (Admin/Manager)

**POST** `/api/ontology/validate`

**Purpose:** SHACL Shape 제약 검증 실행

**Request Body:**

```json
{
  "scope": "all" | "snapshot",
  "snapshotId": "UUID"
}
```

## 12. 릴리스 조건

08-A, 08-B 테스트를 통과해야 릴리스 가능하다. Snapshot 생성 시 SHACL 검증 실패나 SWRL 불일치가 발생하면 API가 에러를 반환해야 하고, SPARQL 엔드포인트로 Triple Store를 직접 수정하는 건 차단한다.
