# 10. CAS_Ontology_Specification

## 1. Document Purpose

CAS의 **OWL 2 DL 온톨로지 스키마, 추론 엔진, SHACL 제약, SWRL 규칙**을 정의한다.

온톨로지가 있는 이유는 간단하다. 계산·평가 로직을 **형식 논리로 표현**해서, 도메인 제약을 사람이 아니라 기계가 검증할 수 있게 하려는 것이다.

아래 문서들의 규칙을 온톨로지 레벨로 옮긴다.

* 01. CAS_Decision_n_Data_Immutability_Contract
* 03. CAS_Data_Model_n_Snapshot_Schema
* 04. CAS_Calculation_Engine_n_Cost_Rule_Spec
* 05. CAS_Target_n_Evaluation_Logic_Spec

---

## 2. Ontology Architecture

### 2.1 Technology Stack

| Component         | Technology                    | Role                           |
| ----------------- | ----------------------------- | ------------------------------ |
| Ontology Language | OWL 2 DL                     | 클래스·프로퍼티·공리 정의                 |
| Constraint Layer  | SHACL (Shapes Constraint)     | 데이터 무결성 제약 검증                   |
| Inference Rules   | SWRL (Semantic Web Rule Lang) | 계산·평가 추론 규칙 정의                  |
| Triple Store      | Apache Jena TDB2 / Stardog   | RDF 트리플 영속화                     |
| Reasoner          | Apache Jena Reasoner / HermiT | OWL 2 DL 추론 엔진                 |
| Query Interface   | SPARQL 1.1                    | 온톨로지 기반 의미 질의                   |

---

### 2.2 Deployment Model

```
[PostgreSQL] ──(Domain Event)──> [Triple Store Sync Service] ──> [Triple Store]
                                                                       │
                                                                 [SHACL Validator]
                                                                 [SWRL Inference Engine]
                                                                 [SPARQL Endpoint]
```

* 온톨로지 엔진(Apache Jena Fuseki)은 CAS 웹 서버와 함께 **독립 프로세스**로 로컬 실행된다.
* Triple Store는 PostgreSQL로부터 **도메인 이벤트 기반으로 동기화**된다.
* 추론은 Snapshot 생성 시점에 **동기적으로 실행**되며, 조회 시에는 사전 추론된 결과를 반환한다.

---

### 2.3 Dual Store Principle

| 관점     | PostgreSQL (Relational)     | Triple Store (Ontology)          |
| ------ | --------------------------- | -------------------------------- |
| 역할     | 쓰기 측 원본(Write-side SOT)     | 추론 측 원본(Reasoning-side SOT)     |
| 쓰기 경로  | API → PostgreSQL            | PostgreSQL → Event → Triple Store |
| 읽기 경로  | SQL (트랜잭션 조회)               | SPARQL (의미 질의)                   |
| 무결성 강제 | DB 제약(FK, UNIQUE, CHECK)    | SHACL Shape 검증                   |
| 추론     | 없음                          | SWRL 규칙 기반 추론                    |

※ PostgreSQL과 Triple Store는 상호 대체 관계가 아니며, 상호 보완적이다.

---

### 2.4 Closed-World Enforcement

OWL의 기본 가정은 **개방 세계 가정(OWA)** 이나, CAS는 **폐쇄 세계 가정(CWA)** 을 채택한다.

이를 위해:

* SHACL Shape로 **필수 트리플의 존재 여부를 강제**한다 (트리플 부재 = 오류).
* OWL 개방 세계 추론은 사용하지 않는다 (미지(unknown) 상태 불허).
* 모든 Snapshot은 정의된 CostItem 집합에 대한 값을 **완전히 포함**해야 한다.

### 3.3 Class Axioms (OWL Restrictions)

```
cas:Snapshot:
  owl:hasKey(cas:snapshotId)
  # Immutability: 생성 후 모든 프로퍼티 수정 불가 (SHACL로 강제)

cas:Vehicle:
  owl:maxCardinality(1, cas:hasBidSnapshot)
  # 각 Vehicle은 정확히 하나의 Bid Snapshot만 가짐

cas:Stage:
  owl:oneOf(cas:BID_STAGE, cas:DC1_STAGE, cas:DC2_STAGE,
            cas:DC3_STAGE, cas:SOP_STAGE, cas:POST_SOP_STAGE)
  # Stage는 정의된 열거형의 Named Individual
```

## 6. SHACL Constraint Shapes

### 6.1 SnapshotImmutabilityShape

**Purpose:** 생성 완료된 Snapshot의 모든 프로퍼티 수정을 금지한다 (01 §2.2 강제).

```turtle
cas:SnapshotImmutabilityShape a sh:NodeShape ;
  sh:targetClass cas:Snapshot ;
  sh:description "Snapshot은 생성 이후 수정·삭제·재계산이 불가하다" ;
  sh:severity sh:Violation .
```

※ 구현 시 Triple Store의 UPDATE/DELETE 연산 자체를 차단해서 지킨다.

---

### 6.2 StageTransitionShape

**Purpose:** Stage Snapshot의 선형 진행 규칙을 검증한다 (03 §3.2).

```turtle
cas:StageTransitionShape a sh:NodeShape ;
  sh:targetClass cas:Snapshot ;
  sh:property [
    sh:path cas:basedOnSnapshot ;
    sh:description "Bid 이외의 Snapshot은 반드시 직전 Stage의 Snapshot을 참조해야 한다" ;
    sh:minCount 1 ;  # Bid 제외
  ] .
```

※ Bid Snapshot은 `cas:basedOnSnapshot`이 NULL인 유일한 Snapshot이다.

---

### 6.3 BidUniquenessShape

**Purpose:** Vehicle당 Bid Snapshot이 딱 하나만 있는지 확인한다 (03 §2.3).

```turtle
cas:BidUniquenessShape a sh:NodeShape ;
  sh:targetClass cas:Vehicle ;
  sh:property [
    sh:path cas:hasSnapshot ;
    sh:qualifiedValueShape [
      sh:property [ sh:path cas:snapshotType ; sh:hasValue "BID" ]
    ] ;
    sh:qualifiedMaxCount 1 ;
  ] .
```

---

### 6.4 SnapshotAtomicityShape

**Purpose:** Snapshot에 필수 CostItem이 빠짐없이 들어있는지 확인한다 (03 §6.1).

```turtle
cas:SnapshotAtomicityShape a sh:NodeShape ;
  sh:targetClass cas:Snapshot ;
  sh:description "Snapshot은 정의된 모든 INPUT CostItem에 대한 값을 포함해야 한다" ;
  sh:property [
    sh:path cas:hasCostValue ;
    sh:minCount 5 ;  # PRICE, MAT, ASM, LOG, PKG
  ] .
```

---

### 6.5 InputValidationShape

**Purpose:** INPUT 비용 항목의 무결성 규칙을 검증한다 (04 §6.1).

```turtle
cas:InputValidationShape a sh:NodeShape ;
  sh:targetClass cas:SnapshotCostValue ;
  sh:property [
    sh:path cas:value ;
    sh:minInclusive 0 ;
    sh:datatype xsd:decimal ;
    sh:description "핵심 비용 항목은 음수가 될 수 없다" ;
  ] .
```

※ 음수 허용 항목(CASHBACK, DEV_REC)은 별도 Shape로 예외 처리한다.

---

### 6.6 BidNonEvaluableShape

**Purpose:** Bid Stage에 대한 평가 결과 생성을 금지한다 (05 §5.1 강제).

```turtle
cas:BidNonEvaluableShape a sh:NodeShape ;
  sh:targetClass cas:Snapshot ;
  sh:sparql [
    sh:message "Bid Snapshot은 평가 대상이 아니다" ;
    sh:select """
      SELECT $this WHERE {
        $this cas:snapshotType "BID" .
        $this cas:evaluatedBy ?eval .
      }
    """ ;
  ] .
```

## 7. SWRL Inference Rules

### 7.1 Calculation Inference Rules

#### SWRL-CALC-001: Total Revenue (per-unit)

```
cas:Snapshot(?s) ∧ cas:hasCostValue(?s, ?cv) ∧ cas:forCostItem(?cv, cas:PRICE)
∧ cas:value(?cv, ?v)
→ cas:totalRevenue(?s, ?v)
```

#### SWRL-CALC-002: Total Cost (per-unit, Standard)

```
cas:Snapshot(?s) ∧ cas:hasCostValue(?s, ?cv_m) ∧ cas:forCostItem(?cv_m, cas:MAT_UNIT) ∧ cas:value(?cv_m, ?m)
∧ cas:hasCostValue(?s, ?cv_a) ∧ cas:forCostItem(?cv_a, cas:ASM_UNIT) ∧ cas:value(?cv_a, ?a)
∧ cas:hasCostValue(?s, ?cv_l) ∧ cas:forCostItem(?cv_l, cas:LOG_UNIT) ∧ cas:value(?cv_l, ?l)
∧ cas:hasCostValue(?s, ?cv_k) ∧ cas:forCostItem(?cv_k, cas:PKG_UNIT) ∧ cas:value(?cv_k, ?k)
∧ swrlb:add(?sum1, ?m, ?a) ∧ swrlb:add(?sum2, ?sum1, ?l) ∧ swrlb:add(?tc, ?sum2, ?k)
→ cas:totalCost(?s, ?tc)
```

#### SWRL-CALC-003: Cost Ratio

```
cas:Snapshot(?s) ∧ cas:totalCost(?s, ?tc) ∧ cas:totalRevenue(?s, ?tr)
∧ swrlb:divide(?ratio, ?tc, ?tr)
→ cas:costRatio(?s, ?ratio)
```

---

### 7.2 Evaluation Inference Rules

#### SWRL-EVAL-001: GREEN Status

```
cas:EvaluationResult(?e) ∧ cas:metricValue(?e, ?mv) ∧ cas:againstTarget(?e, ?t)
∧ cas:targetValue(?t, ?tv) ∧ swrlb:lessThanOrEqual(?mv, ?tv)
→ cas:evaluationStatus(?e, "GREEN")
```

#### SWRL-EVAL-002: YELLOW Status

```
cas:EvaluationResult(?e) ∧ cas:metricValue(?e, ?mv) ∧ cas:againstTarget(?e, ?t)
∧ cas:targetValue(?t, ?tv) ∧ cas:warningThreshold(?t, ?wt)
∧ swrlb:add(?upper, ?tv, ?wt)
∧ swrlb:greaterThan(?mv, ?tv) ∧ swrlb:lessThanOrEqual(?mv, ?upper)
→ cas:evaluationStatus(?e, "YELLOW")
```

#### SWRL-EVAL-003: RED Status

```
cas:EvaluationResult(?e) ∧ cas:metricValue(?e, ?mv) ∧ cas:againstTarget(?e, ?t)
∧ cas:targetValue(?t, ?tv) ∧ cas:warningThreshold(?t, ?wt)
∧ swrlb:add(?upper, ?tv, ?wt)
∧ swrlb:greaterThan(?mv, ?upper)
→ cas:evaluationStatus(?e, "RED")
```

---

### 7.3 Decision Ownership Inference

```
cas:CostItem(?c) ∧ cas:semanticType(?c, "INPUT")
→ cas:decisionOwner(?c, "Human/ExternalSystem")

cas:CostItem(?c) ∧ cas:semanticType(?c, "AGGREGATED")
→ cas:decisionOwner(?c, "RuleEngine")

cas:CostItem(?c) ∧ cas:semanticType(?c, "DERIVED")
→ cas:decisionOwner(?c, "RuleEngine")
```

## 8. SPARQL Query Patterns

### 8.1 Vehicle Risk Query

```sparql
SELECT ?vehicle ?stage ?status WHERE {
  ?vehicle rdf:type cas:Vehicle .
  ?vehicle cas:hasSnapshot ?snapshot .
  ?snapshot cas:evaluatedBy ?eval .
  ?eval cas:evaluationStatus ?status .
  ?eval cas:inView cas:VIEW_INIT .
  ?snapshot cas:stage ?stage .
}
ORDER BY ?status
```

### 8.2 Snapshot Cost Structure Query

```sparql
SELECT ?costItem ?value WHERE {
  ?snapshot cas:snapshotId "UUID" .
  ?snapshot cas:hasCostValue ?cv .
  ?cv cas:forCostItem ?costItem .
  ?cv cas:value ?value .
}
```

### 8.3 Stage Transition Chain Query

```sparql
SELECT ?snapshot ?stage ?baseSnapshot WHERE {
  ?snapshot rdf:type cas:Snapshot .
  ?snapshot cas:basedOnSnapshot ?baseSnapshot .
  ?snapshot cas:stage ?stage .
}
ORDER BY ?stage
```

## 9. Ontology Versioning Policy

* 온톨로지 스키마 버전은 `cas:ontologyVersion`으로 관리되며, Snapshot의 `calculation_version`과 함께 기록된다.
* SWRL 규칙 변경은 **계산 버전 변경에 해당**한다.
* 온톨로지 스키마 변경은 **기존 Snapshot의 트리플에 영향을 미치지 않는다** (불변성 원칙).
* 새로운 온톨로지 버전은 이후 생성되는 Snapshot에만 적용된다.
* Triple Store 마이그레이션은 스키마 호환성이 유지되는 범위에서만 허용된다.

## 10. Dual Verification Protocol

CAS는 계산 엔진과 SWRL 추론 엔진으로 **이중 검증**을 한다.

```
Snapshot 생성 시:
  1. 결정론적 계산 엔진이 INPUT → AGGREGATED → DERIVED 결과를 산출
  2. SWRL 추론 엔진이 동일 INPUT 트리플에 대해 추론을 실행
  3. 두 결과를 비교: 불일치 발생 시 Snapshot 생성 중단 (BLOCKER)
  4. 일치 확인 후 Snapshot 확정, Triple Store에 결과 트리플 영속화
```

※ 이중 검증은 온톨로지 규칙과 도메인 계산 로직이 같은 결과를 내는지 확인하는 안전 장치다.

---

## 11. 변경 시 주의

SHACL 제약 위반이나 SWRL–계산엔진 결과 불일치는 **BLOCKER**로 취급한다. 온톨로지 스키마를 바꾸면 01, 03, 04, 05 문서와 맞는지 반드시 확인한다.
