# 00. CAS_System_Overview

## 1. System Name

**CAS (Cost Analysis System)**

## 2. System Purpose

CAS는 신차 수주 시점부터 양산 단계까지의 **차종–품번–단계(Stage) 기준 비용 구조를 정형 데이터로 축적**하고, 규칙 기반 연산을 통해 **각 설계원가(Stage) 단계별 비용 변화, 초도가 및 5년 평균 기준의 원가·수익성·목표 달성 여부를 자동 산출**하는 내부 AX 시스템이다.

CAS의 목적은 단순한 분석 자동화가 아니라, **"과거 특정 시점의 비용 판단이 언제, 누구에 의해, 어떤 기준으로 이루어졌는지"를 재현 가능한 상태로 고정**하는 데 있다.

본 시스템의 목적은 다음 세 가지로 한정된다.

1. 비용 분석에 소요되는 반복 업무를 시스템으로 대체
2. 수주 이후 설계원가(Stage) 단계별 비용 변동을 **시점 고정 데이터(snapshot)**로 보존
3. 각 설계 단계에서의 비용 증감 이력을 기반으로, **다음 단계에서의 목표 인상·절감 폭을 사전에 설정**할 수 있도록 판단 근거를 제공

※ CAS는 ‘의사결정 자동화 시스템’이 아니다.
※ CAS는 **의사결정을 위한 계산 결과와 판단 근거를 시간 축 위에 고정하는 시스템**이다.

## 3. Problem Definition (Why CAS)

### 3.1 기존 방식의 문제

* 비용 분석이 엑셀 파일 단위로 분산되어 있음
* 계산 로직이 개인별·파일별로 상이함
* 과거 수주 시점의 기준 데이터가 보존되지 않음
* 목표가 설정이 경험·감각에 의존함

### 3.2 CAS가 해결하는 문제

* 모든 비용 데이터를 **차종-품번-단계(Stage) 기준으로 구조화**

※ 본 시스템에서 말하는 ‘단계(Stage)’란, 수주 이후 개발 기간 동안 진행되는 설계원가 단계(설원1차·2차·3차), 양산 초도가, 양산 후 설변 단계를 의미하며, 연차(Year) 기준 관리와는 구분된다.

* 모든 계산 로직을 규칙 엔진으로 고정
* 수주 시점 기준 데이터 스냅샷 보존
* 목표 기준(80% / 100%)의 자동 역산 제공

## 4. System Scope

### 4.1 포함 범위 (In Scope)

* 차종 단위 비용 구조 관리
* 품번 단위 상세 원가 관리
* 관리 데이터(인건비, 환율) 기준 적용
* 초도가 / 5년 평균 기준 분석
* 목표 달성 여부 판단
* 미달성 시 리포트 메일 발송
* OWL 2 DL 온톨로지 기반 도메인 의미 표현 및 SWRL/SHACL 추론·제약 검증

### 4.2 제외 범위 (Out of Scope)

* 원가 예측 모델링 (ML 기반)
* 외부 고객용 공개 시스템
* ERP 데이터 수정
* 자동 의사결정 및 승인 기능
* 개방 세계 추론(Open-World Reasoning) 및 확률적 추론

## 5. Users & Roles

| Role    | Description                                 |
| ------- | ------------------------------------------- |
| Admin   | 시스템 전체 관리, 사용자 관리                           |
| Manager | 차종 분석 조회, 코멘트 수정 및 승인, 리포트 설정, 기준 데이터 수정 승인 |
| Analyst | 데이터 입력, Snapshot 생성, 코멘트 작성, 기준 데이터 수정     |

> **v1.1 변경:** 기존 `Staff` 역할명을 `Analyst`로 변경. 비용 분석 업무 도메인에 더 적합한 명칭이며, RBAC에서 `ANALYST`로 구현됨.

## 6. High-level Architecture

```
[User]
  └─ Next.js 15 Dashboard (App Router, SSR)
       └─ Node.js API Server (Next.js Route Handlers)
            ├─ PostgreSQL 17 (Relational Persistence, Write-side SOT)
            │    ├─ Raw Input Tables (Vehicle, Part, VehicleVolume)
            │    ├─ Snapshot Tables (Immutable — DB Trigger 차단)
            │    ├─ CostComponent Catalog (A/B/C Type 통합)
            │    └─ Reference Tables (Labor, FX — 지역×연도별)
            ├─ Authentication (NextAuth.js Credentials, JWT 8h, RBAC 4-Role)
            ├─ Ontology Engine (OWL 2 DL, Reasoning-side SOT) ← Phase 8
            │    ├─ Triple Store (Materialized Semantic View)
            │    ├─ SHACL Constraint Validator
            │    ├─ SWRL Inference Engine
            │    └─ SPARQL Query Endpoint
            ├─ Calculation Engine (Deterministic, Pure Function, Decimal.js)
            ├─ Rule-based Evaluation Logic (2-Scenario: 매출원가율 80% / 총비용율 100%)
            └─ Report Mailer (MJML + Nodemailer)
```

> **v1.1 구현 반영:** 인증은 NextAuth.js Credentials Provider(JWT 8h 세션)로 구현. ORM은 Prisma 6. Ontology Engine은 Phase 8에서 통합 예정.

Snapshot Tables는 한 번 생성되면 재계산이나 덮어쓰기가 불가하고, 모든 분석 결과는 반드시 Snapshot 기준으로만 산출된다. 온톨로지 엔진은 이러한 계산·평가 규칙을 형식 논리로 표현해서, 도메인 제약이 기계적으로 검증되도록 한다 (상세: 10. CAS_Ontology_Specification).

## 7. AX Design Principle

### 7.1 Decision Ownership

* 모든 **수치 계산과 목표 판단은 규칙 엔진이 담당**
* 온톨로지 추론 엔진(SWRL)은 규칙 엔진의 **형식 논리적 구현체**이며, 별도의 의사결정 주체가 아니다
* LLM은 계산 결과를 요약·설명하는 텍스트 생성에만 사용 가능
* LLM의 출력은 시스템 판단에 영향을 미치지 않는다

### 7.2 Temporal Immutability (시간 불변성)

* 수주 시점, 양산 개시 시점의 모든 입력값은 **Snapshot으로 고정**
* Snapshot 이후의 기준 데이터 변경은 과거 결과에 영향을 주지 않는다

### 7.3 Deterministic First

* 같은 Snapshot 입력이면 언제든 같은 결과가 나와야 한다
* 계산 로직은 버전 관리되며, 결과에 적용된 로직 버전이 기록된다
* 온톨로지 추론은 OWL 2 DL의 결정가능성(decidability)에 기반하므로, 같은 트리플이 입력되면 추론 결과도 항상 같다

### 7.4 Human-in-the-loop

* 담당자 코멘트는 판단의 *해석* 영역으로만 사용된다
* 수치·판정 결과는 사용자가 수정할 수 없다

## 8. Success Criteria

* 동일 차종 재분석 시 결과 일관성 100%
* 분석 시간 기존 대비 70% 이상 단축
* 목표 미달성 항목 자동 식별 정확도 100%

## 9. Non-goals

* 비용을 줄여주는 시스템이 아님
* 판단을 대신 내려주는 시스템이 아님

이하 기능·데이터·UI 명세는 이 Overview와 일치해야 한다.
